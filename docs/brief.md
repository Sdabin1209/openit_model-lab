# 영역 브리프: 모델 개발·평가 (model-lab)

> **계약 상태.** 영역 사이 계약은 `../boundary-contracts`(헤드 소유)에 있고, 이 브리프의 계약 이름은 `head/docs/STRUCTURE.md`의 제안이다. 초안이 있는 것은 ReleaseManifest, GateDecision, TraceEnvelope뿐이고 나머지 필드는 헤드가 사용자와 논의해 확정 중이다. 확정 전에는 **계약에 의존하지 않는 부분**(내부 설계, 도메인 모델, 테스트 틀)만 진행한다. 계약이 부족하다고 느끼면 임의로 가정하지 말고 `docs/change-requests/`에 쓴다.
> **읽기.** `../boundary-contracts`와 `../survey-service/schema`는 문진 서비스의 데이터 스키마(스키마만 남긴 최소 구성)다. 구현이 가져가는 계약은 `schemas/<계약명>.json`(JSON Schema Draft 2020-12), 컴포넌트별 입력·출력 대응은 `COMPONENTS.yaml`, 정수 버전은 `CONTRACT_VERSION`이다. 둘 다 읽기 전용이다.
> **버전(D14, D19).** 문진 스키마는 정수 버전(`CONTRACT_VERSION`, 현재 1)에 정확히 일치해야 한다. 경계 계약은 `MAJOR.MINOR`이며 값은 `boundary-contracts`가 정한다. 불변 산출물은 `ArtifactRef`(id, version, content_hash)로 가리킨다.

## 1. 목적과 범위

- 목적: Parser의 LoRA-A와 Generator의 LoRA-B를 학습·평가하고, 서빙 가능한 패키지로 모델 레지스트리에 올린다. 프로젝트에서 사용자가 가장 집중하려는 영역이다.
- 하는 일: 데이터셋 로딩, 학습, 실험 추적, Parser·Generator 평가, 턴 시뮬레이션, 회귀 평가, 보고서 작성, 모델 패키징.
- 하지 않는 일: 통과 임계치·지표·평가셋 구성을 임의로 정하지 않는다(O11, 사용자와 함께 정한다). 릴리스 승인(게이트).

## 2. 소유하는 것

- 소유 저장소: 모델 레지스트리(불변 패키지).
- 제공하는 SDK 인터페이스: 모델 게시 SDK(쓰기), 모델 읽기 SDK(패키지 조회). 소비자는 게이트.
- 이 SDK의 메모리 구현(가짜 구현)을 함께 배포한다.
- 생산하는 계약: `ModelPackageManifest`.

## 3. 소비하는 것

- 소비하는 계약: `ParserSample`, `GeneratorSample`, `DatasetManifest`, `FailureCase`, `QuestionBank`, `GateDecision`.
- 소비하는 SDK: 데이터셋 읽기 SDK(synthetic-data), 실패 사례 읽기 SDK(ops-feedback), 문항 읽기 SDK(question-authoring, D13), 판정 조회 SDK(release-gate). 라이브러리로 turn-engine, model-runtime, 문진 스키마.
- 지원하는 계약 버전: 문진 스키마 정수 버전, 경계 계약 `MAJOR.MINOR`.

## 3-1. 경계 명세 (블랙박스 기준)

상대 영역은 블랙박스다. 아래 인터페이스 번호의 시그니처, 오류, 멱등성은 `../boundary-contracts/INTERFACES.md`와 `CONVENTIONS.md`가 정한다. 이 명세 밖의 것을 상대에게 기대하거나 가정하지 않는다.

- 내는 것: **I3** ModelRegistry(`ModelPackageManifest`, 어댑터, 평가 리포트).
- 받는 것: **I2**(데이터셋), **I1**(문항 정의, D13), **I7**(회귀 케이스), **I4**(판정 조회), **I8**, **I9**.
- 해야 하는 것: 평가를 서비스와 같은 I8·I9로 수행한다. 패키지 매니페스트에 학습 계보(데이터셋 버전, 라이브러리 버전)를 모두 적는다. 평가 리포트의 형식은 영역이 정한다(게이트는 해석하지 않는다).

## 4. 상위 수용 기준

- 패키지는 불변이다. 어댑터 해시, 기반 모델, 서빙 설정, 학습 계보(데이터셋 버전과 실험), 평가 리포트 참조가 매니페스트에 있다.
- 평가는 서비스와 같은 model-runtime·turn-engine으로 수행해 서빙 동작을 재현한다.
- 평가를 문항 유형·단위·범위별로 쪼개 볼 수 있다(D13).
- 회귀 평가가 실패 사례(정답 있는 것)를 포함한다.
- 학습 데이터에 평가셋이 섞이지 않는다.
- 모델은 문항이 입력으로 주어지면 처음 보는 문항도 다루도록 만드는 것이 목적이다(D32). 학습은 문항 정의에 의존하는 표현이 아니라 문항을 읽고 일반화하도록 설계하고, 평가는 보지 못한 문항 세트에 대한 성능을 따로 보고한다.
- 보지 못한 문항에서의 추출 실패는 오류이며 `FailureCase`로 돌아와 그 문항의 샘플 생성과 재학습의 입력이 된다.
- 어떤 임계치도 사용자 확정 없이 기본값으로 박혀 있지 않다.
- 학습·평가·패키징·게시는 **설정 파일 하나로 반복 실행되는 파이프라인**이다(D38, D39). 손으로 명령을 이어 치지 않는다. 입력은 데이터셋 버전과 학습 설정이고, 같은 입력과 시드는 같은 결과를 낸다. 중간에 멈추면 이어서 실행할 수 있다. 실행마다 설정, 시드, 데이터셋 버전, 라이브러리 버전, 결과가 기록되어 실험을 비교할 수 있다.
- 새 데이터셋 버전이 게시되면 정해진 설정으로 자동 실행할 수 있다(저장소를 보고 일한다, D39). 학습 방법과 하이퍼파라미터는 시행착오의 대상이라 설정으로 바꿀 수 있어야 하며, 이 단계에서 성능을 맞추는 것은 목표가 아니다. 파이프라인이 끝까지 도는 것이 목표다.

## 5. 비기능 요구

- 지연·가용성: 요구 없음.
- 자원: GPU. 학습·평가는 운영 서버 밖에서 돌리고 결과만 게시하기를 권한다.
- 보안·개인정보: 학습 데이터에 비식별되지 않은 발화를 쓰지 않는다.

## 6. 건드리면 안 되는 경계

- 모델 레지스트리에 쓰는 영역은 이 영역뿐이다. 게이트를 거치지 않은 모델은 서비스에 갈 수 없다.
- 데이터셋·문항·실패 사례는 읽기 SDK로만 읽는다.

## 7. 이 영역에 해당하는 열린 결정

- O11 평가셋 구성: 사용자 결정, 지표·통과 임계치·실패 유형 분류체계도 포함. **정해질 때까지 평가기의 임계치 부분은 비워 둔다.**
- O14 모델 출력 형식 보장 방식: model-runtime과 협의가 필요하면 변경 요청으로 올린다.

## 8. 시드

데이터셋 로더, LoRA-A·B 학습기, 실험 추적기, Parser·Generator 평가기, 턴 시뮬레이터, 회귀 평가기, 보고서 작성기, 모델 패키저.

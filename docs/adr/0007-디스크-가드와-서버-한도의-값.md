# 0007. 디스크 가드와 서버 한도의 값과 근거

- 상태: 채택됨. **값 대부분은 측정하지 않은 시작값이다.** 측정이 생기면 이 ADR을 대체한다.

## 맥락
gpu-dev는 WSL2 사용자 워크스테이션이다. `df`는 가상 디스크 크기(1007GB)만 보여 주고 호스트 여유를 모르며, 지워도 vhdx가 줄지 않는다(`docs/runbook.md` D61 절, 2026-10-15 관찰; 직접 확인한 값은 작업 폴더 약 15GB, 모델 캐시 2.9GB). 모델 하나(Qwen3-8B 등)를 내려받으면 수~수십 GB다. 레지스트리 서비스는 최대 4GiB 본문을 받는다. 점검 ML-1/ML-2가 한도 부재를 지적했다.

## 결정과 값별 근거
| 값 | 위치 | 근거 |
| --- | --- | --- |
| 모델 내려받기 예산 `max_footprint_gb: 20` | `configs/compare/*.yaml` | (HF 캐시 + `~/openit-gpu` + 후보 예상 크기)로 `df` 대신 우리 작업의 사용량만 센다. 표준이 없는 호스트 제약(WSL df)에서 나온 방식이다. 20이라는 숫자의 출처는 **근거 기록 없음**(측정 안 함; 관찰 당시 15+2.9GB라 새 모델 하나로 넘기게 된다는 점만 runbook에 있다). 사용자와 정하기로 했다(D61 runbook). 실제(`hf`) 백엔드에서만 적용한다. 가짜 백엔드는 내려받지 않는다. |
| 학습 전 `min_free_gb` 기본 30, `disk_policy` block | `train_wrap.py` | 학습 출력은 어댑터(작음)이지만 체크포인트·캐시가 쌓일 수 있다는 가정. 30의 출처는 **근거 기록 없음**(측정 안 함). `df`를 쓰므로 WSL에서는 부정확해 `warn`/`off`를 설정으로 고를 수 있다. 막지 않고 경고만 하던 이전 동작은 ML-2로 바꿨다(FAULT_POLICY 13항: 디스크가 차면 막고 알린다). |
| 게시 여유 = 본문 2배 + `MIN_FREE_GB` 1 | `service/app.py` | 본문 tar와 풀어 둔 사본이 동시에 있는 최대 순간이 2배(본문 삭제 후 저장은 하드 링크라 추가 사본이 없다). +1GB는 근거 기록 없음. 이전에는 최대 약 3배였다(코드로 확인). |
| 본문 상한 4GiB | `MODEL_REGISTRY_MAX_BODY` | 어댑터는 LoRA라 작다는 가정의 여유값. 근거 기록 없음(측정 안 함). |
| 소켓 timeout 30초 | `MODEL_REGISTRY_SOCKET_TIMEOUT` | 느린 클라이언트가 스레드를 잡는 시간의 상한. 클라이언트 기본 timeout(10초, HttpClientBase)보다 길게 잡았다(추정). 측정 안 함. |
| 동시 연결 32, 동시 게시 1 | `…MAX_CONNECTIONS`, `…MAX_PUBLISHES` | 소비자가 소수이고 게시는 파일 잠금으로 직렬화되므로 대기시키지 않고 503으로 되돌린다(재시도 가능, HTTP.md의 503=UNAVAILABLE). 32는 측정 안 함. |
| 인증 실패 10회/60초/주소 | `…AUTH_FAIL_LIMIT` | 반복 추측만 막는 보수값. 표준 값이 아니다. 측정 안 함. **유효하지 않은 토큰을 보낸 요청에만** 적용한다: 토큰 검증을 먼저 하고 유효하면 통과한다(주소 단위로 정상 호출자까지 막으면 프록시·Docker 뒤에서 서비스 전체가 막힌다 — 재점검 ML-1). |
| 종료 유예 8초 | `…SHUTDOWN_GRACE` | Docker의 기본 정지 유예 10초(그 뒤 SIGKILL)보다 짧게. 8은 측정 안 함. 유휴 keep-alive 연결은 소켓 timeout(30초)을 기다리지 않고 즉시 닫는다(재점검 ML-2). |
| 거절 전 본문 버리기 1MiB, 다음 조각 대기 0.25초 | `DRAIN_CAP`, `DRAIN_IDLE` | 거절이 최대 4GiB를 읽는 자원 소모 경로가 되지 않게 하되, 작은 본문은 버려 클라이언트가 연결 초기화 대신 실제 오류(403 등)를 보게 한다(커밋 73fae94의 간헐 실패). 두 값 모두 근거 기록 없음(측정 안 함). 1MiB보다 큰 본문을 보내던 클라이언트는 연결 초기화를 볼 수 있는 것을 감수한다. |

## 왜
표준이 있는 부분: 503 UNAVAILABLE(재시도 가능, HTTP.md), 비밀을 로그에 남기지 않기(D84), 상수 시간 토큰 비교(코드). 표준이 없는 부분은 위 표처럼 제약(WSL df)이나 가정에서 나왔고 **어느 것도 부하 측정으로 얻은 값이 아니다.**

## 검토한 대안과 버리는 이유
- `df`로만 점검: WSL에서 틀리다(runbook 관찰). 그래서 내려받기에는 쓰지 않는다.
- 대기열로 동시 게시를 받기: 대기 중 연결과 `.tmp`가 늘어 자원 한도가 흐려진다. 즉시 503으로 거절하고 클라이언트(release-gate 등)의 재시도에 맡긴다.
- 요청 속도 제한 라이브러리: 의존을 늘리지 않으려고 표준 라이브러리로 주소별 실패 횟수만 센다(ADR 0010).

## 결과
얻는 것: 디스크 고갈과 느린 연결/반복 추측으로 서비스가 멈추는 길을 줄임. 감수하는 것: 값이 실제 부하에 맞는지 모른다. 프록시 뒤에서는 `client_address`가 프록시 주소라 틀린 토큰을 보내는 호출자끼리 한도를 공유한다(정상 토큰은 영향 없음). 실제 출발지를 쓰려면 프록시 헤더를 믿을지 정해야 한다(deploy 구성이 정해지면 결정).

## 되돌리는 조건
용량·처리량을 측정하면(ML-17) 값을 측정치로 바꾸고 새 ADR로 대체한다. 운영 접근 방식(프록시, TLS)이 정해지면 인증 실패 제한의 기준 주소를 다시 정한다.

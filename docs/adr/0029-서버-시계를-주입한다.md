# 0029. model-registry 서버의 시계와 sleep을 주입한다

## 상태
채택 (2026-10-31, 헤드 지시서 U422). 동작(와이어 형식, HTTP 응답)은 바꾸지 않는다.

## 맥락
`link_registry_serve`가 `time.monotonic`(인증 실패 제한의 창, drain의 유예), `time.sleep`(drain 폴링), `time.strftime`(게시자 기록의 `published_at`)을 직접 읽었다. 시험은 이 시간을 실제로 기다리거나(sleep, 소켓 timeout, 실제 프로세스에 신호) 재서(`elapsed < N`) 판정했고, 기계가 바쁘면 합격·불합격이 달라졌다.

## 결정
- `Service(clock=, utc_now=)`와 `drain(srv, grace, log, *, clock, sleep)`이 시계와 sleep을 인자로 받는다. 컴포넌트는 `time`을 import하지 않는다. 진입점 `service/app.py`가 실제 `time.monotonic`/`time.sleep`/UTC 문자열 함수를 넣는다.
- 시험은 가짜 시계(`FakeClock`)를 넣고 시간을 직접 흘린다(61초 지남, 유예 8초 만료). 실제로 기다리는 시간은 0이다.
- waitress의 연결 시한, 신호 처리, link의 413 등 라이브러리 안의 시간은 시험하지 않는다. 라이브러리에 넘기는 값(`channel_timeout`, `connection_limit`, `max_request_body_size`, `threads`)과 종료 신호 처리기가 `shutdown_grace`로 drain을 부르는지, 우리 처리(실패 제한, drain 로직)만 시험한다(`tests/test_server_config.py`).

## 왜
의존성 주입은 시간 의존 코드를 시험하는 표준 방법이다. 시험이 시간을 쥐어야 판정이 부하와 무관해진다.

## 검토한 대안과 버리는 이유
- 전역 time 패치(freezegun, `monkeypatch.setattr(time, ...)`): `Event.wait`·소켓 timeout 같은 블로킹 대기를 움직이지 못하고, 다른 스레드(waitress)의 시간까지 바꾼다.
- 상한을 늘려 덜 깨지게 하기(U420): 부하가 더 크면 다시 깨진다. 판정이 시간에 달린 채다.
- 실제 서버를 띄워 시간을 재는 시험 유지: 확인하려는 것이 라이브러리 동작이라 영역 시험의 몫이 아니다.

## 결과
- 얻는 것: 시험이 시간에 대해 결정적이다. 인증 실패 제한과 drain 로직을 가짜 시계로 모든 경계(창 만료, 유예 만료)에서 시험한다.
- 감수하는 것: 실제 waitress에서 유휴 연결이 닫히는지, 신호 아래 업로드가 끝나는지는 영역 시험이 확인하지 않는다(smoke·E2E의 몫, `tests/TIMING.md` 3절).

## 되돌리는 조건
없음(주입은 비용이 없다). 서버가 link 등 다른 기반으로 바뀌면 이 ADR의 해당 부분을 새 ADR이 대체한다.

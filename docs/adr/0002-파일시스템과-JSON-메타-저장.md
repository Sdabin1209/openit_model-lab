# 0002. 저장소는 파일 시스템 + JSON 메타(DB 없음)

- 상태: 채택됨 (`FileModelRegistry`, `model_lab/registry.py`). 결정 당시의 비교 기록은 없다.

## 맥락
패키지는 쓰기가 드물고(학습 한 번에 역할당 하나) 한 번 쓰면 바뀌지 않으며, 어댑터는 수십 MB~GB의 파일이다. 서버는 단일 호스트 하나를 가정한다(D54: 서빙·백 서버는 RTX 4090 24GB 1장). 헤드의 기본 지침은 "저장소의 실제 기술은 영역이 정한다, 단일 서버 기본값은 DB 인스턴스와 파일 볼륨"이다(`head/docs/DECISIONS.md` O10).

## 결정
`root/manifests/<id>/<버전>.json`(캐노니컬 JSON), `_order.json`(게시 순서), `ids.json`, `adapters/<id>/<버전>/`, `eval_reports/<ref>`, 게시자 기록 `<버전>.published.json`. 쓰기는 파일 잠금(`flock`) 아래 직렬화하고, 각 파일은 임시 파일을 `fsync`한 뒤 `os.replace`로 바꾼다. **매니페스트를 마지막에 쓴다**: 있어야 게시된 것이다.

## 왜
- 불변 레코드와 큰 바이너리가 전부라 관계형 질의가 필요 없다. 필요한 조회는 (id)→버전 목록, (id, 버전)→매니페스트 둘뿐이다(코드로 확인).
- `os.replace`는 같은 파일 시스템에서 원자적이다(POSIX). 매니페스트 마지막 쓰기와 `flock`으로 중단·동시 게시에 안전하다(시험 `tests/test_registry.py`; 중복 버전 결함은 ML-3으로 고쳤다).
- 어댑터를 DB의 blob으로 넣으면 크기와 해시 재검증을 위해 어차피 파일로 풀어야 한다(추정).
- 외부 프로세스가 없어 gpu-dev(Docker·pip 없음)에서도 같은 코드가 돈다.

## 검토한 대안과 버리는 이유
- SQLite 메타 + 파일: 트랜잭션은 좋아지나 이 규모(측정 안 함; 패키지는 역할당 학습 횟수만큼)에서 질의 이득이 없고, 스키마 마이그레이션이 생긴다. 근거 기록 없음(당시 비교 문서 없음) — 위는 현재 판단.
- PostgreSQL: 서버 추가가 필요한데 동시 쓰기 요구가 없다(게시는 한 번에 하나로 직렬화해도 충분, ADR 0007).

## 결과
얻는 것: 단순함, 사람이 파일을 열어 볼 수 있음, 백업은 디렉터리 복사. 감수하는 것: 파일 배치에 버전 표시가 없어 배치 변경 수단이 없다(ML-17), 전원 장애 시 디렉터리 `fsync`는 하지 않는다(파일만 `fsync`), 용량·처리량은 측정하지 않았다(측정 안 함).

## 되돌리는 조건
패키지 수가 목록·검색을 느리게 만들거나(측정 필요), 레지스트리를 여러 호스트에서 쓰기 가능하게 해야 하면 DB 기반으로 바꾸고 새 ADR로 대체한다.

# 0006. 학습 서버 어댑터는 package-adapters로 패키지에 얹는다(평가 없이)

- 상태: 채택됨 (D84; `model_lab/attach.py`)

## 맥락
학습은 서버 코드가 정본이고(ADR 0004) 결과는 사람이 파일로 옮긴다(`docs/runbook.md`). 파이프라인(`run`: 적재→변환→학습→평가→패키징→게시)을 다시 돌리면 이 리포의 비정본 학습기가 어댑터를 새로 만든다. 서버가 만든 어댑터를 그대로 서빙 가능한 패키지로 만들 길이 필요하다.

## 결정
`package-adapters`는 어댑터 디렉터리 두 개 + 시스템 프롬프트 두 개 + 프로파일(기반 모델)을 받아 패키지를 만들고 게시한다. 어댑터는 필수 두 파일만 복사하므로(그 밖의 파일은 해시에 들어가지 않는다) 같은 입력은 같은 패키지가 된다(멱등). 기반 모델 `base_model_name_or_path`와 rank 상한을 프로파일에 대조해 어긋나면 아무것도 게시하지 않는다. 평가는 하지 않고, 리포트는 "평가하지 않았다(n=0)"로 표시한다. 학습 기록(`--train-record-*`)을 주면 대조해 `ext."model-lab".lineage`에 넣고 없으면 경고한다.

## 왜
- 평가를 지어내지 않는다: 평가 값이 없는데 있는 것처럼 쓰지 않는다는 워크스페이스 규칙. 합격 판정은 release-gate 몫이다(브리프 1절).
- 기반 모델·rank 확인: 다른 기반 모델의 어댑터를 얹으면 적재 시 실패하거나 조용히 틀린다(D81: 어댑터와 프로파일의 기반 모델이 다르면 거부).
- 멱등(같은 입력 → 같은 해시): 자동화는 여러 번 실행해도 안전해야 한다(D39).

## 검토한 대안과 버리는 이유
- 파이프라인을 서버 어댑터 입력으로 확장: 변환·학습 단계를 건너뛰는 분기가 생겨 파이프라인 재현성 규칙(같은 설정=같은 결과)이 흐려진다. 근거 기록 없음(당시 비교 문서 없음) — 위는 현재 판단.
- 손으로 매니페스트 작성: 해시와 필드 실수 위험(추정).

## 결과
얻는 것: 서버 어댑터를 평가 없이 즉시 패키지로 올릴 수 있다. 감수하는 것: 계보가 학습 기록의 자기 보고에 의존하고(ML-5), 기반 모델 revision은 사람이 준다(`unspecified` 가능). 학습 기록 필드는 비계약 `ext`라 정식 필드 승격은 변경 요청이 필요하다.

## 되돌리는 조건
파이프라인의 `train` 단계가 감싸기에 연결되면(README) 이 길을 파이프라인의 한 입력 모드로 통합하는 새 ADR을 쓴다.

# 0027. 계약 3.0.0 전환: action_rules_version, 레코드 3.0, 라벨은 실제 설치 버전에서

## 상태
채택 (2026-10-30, 헤드 브리프 u300, boundary-contracts v3.0.0, U50). [ADR 0022](0022-turn-engine-코드-의존을-계약으로-옮긴다.md)의 `turn_engine_version` 표지 부분을 대체한다.

## 맥락
계약 3.0.0이 `turn_engine_version`을 `action_rules_version`으로 바꾸고(값 = `ActionExtractionRules.rules_version`), 이미지 라벨 `io.openit.turn-engine`과 `BuildImageRequest.versions.turn_engine`을 없앴다. 2.x 레코드는 3.0 클라이언트가 UNSUPPORTED_VERSION으로 거부한다. 또 U50: 라벨이 요청 문자열을 옮긴 값이면 실제 설치와 다를 수 있다.

## 결정
- 모델 패키지 매니페스트의 `lineage.action_rules_version`은 설치된 계약 규칙 데이터(`boundary_contracts.action_rules.load_rules()["rules_version"]`)에서 읽는다. 코드에 리터럴이 없다. 설정 `lineage.turn_engine_version`과 `DEFAULT_TURN_ENGINE_MARK`는 지웠다.
- 시험 고정값과 메모리 구현의 레코드는 `PIPELINE_SCHEMA_VERSION`(상수, 3.0)과 위 함수를 쓴다.
- Dockerfile에서 `io.openit.turn-engine` 라벨을 지웠다.
- `scripts/build-image.sh`(U50): `io.openit.contracts.boundary`는 요청이 아니라 실제로 만든 wheel의 버전에서 만든다. 요청 `versions.boundary`가 이 영역의 고정 버전(`requirements-service.txt`)과 다르거나, `dependency_sources.boundary`의 실제 버전이 요청과 다르면 이미지를 만들지 않고 메시지와 함께 종료 2다. 빌드 뒤 이미지 안에서 `importlib.metadata`로 읽은 버전이 라벨과 다르면 이미지를 지우고 실패한다.

## 왜
계약 3.0.0이 정했다. 계보 일치 검사는 이 값으로 한다(release-gate). 라벨은 추적용이라 거짓이면 쓸모가 없다.

## 검토한 대안과 버리는 이유
- 설정에서 값을 받기: 설정과 설치된 규칙이 어긋날 수 있다.
- 요청 버전을 그대로 라벨로: U50이 지적한 거짓 라벨이 가능하다.

## 결과
- 시험: `tests/test_u3_contracts.py`(값이 규칙 데이터와 같고 옛 필드가 없다, 옛 설정 키 거부), `tests/test_build_image.py`(고정 버전과 다른 요청 실패, 다른 버전 소스 실패, 라벨이 이미지 안 실제 버전과 같음).
- 감수: 2.x로 만든 저장소 데이터는 3.0 클라이언트가 읽지 않는다(시연·시험 저장소는 다시 만든다, 계약 CHANGELOG).

## 되돌리는 조건
계약이 다시 바뀌면 따른다.

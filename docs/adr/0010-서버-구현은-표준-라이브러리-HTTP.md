# 0010. 레지스트리 서버는 표준 라이브러리 `http.server`(스레드)로 구현한다

- 상태: 채택됨 (`model_lab/service/app.py`). 선택의 직접 기록은 없다.

## 맥락
서비스 이미지는 `boundary-contracts`(와 `jsonschema`)만 넣고 root가 아닌 사용자로 돈다(`Dockerfile`, 워크스페이스 규칙). 요청은 소수(게시 드묾, 조회 소수 소비자)이고 본문이 큰 tar 스트림이다.

## 결정
`ThreadingHTTPServer` 기반 서버, 연결당 스레드, 파일 잠금으로 게시 직렬화. 동시 연결·게시 상한과 소켓 timeout을 직접 둔다(ADR 0007). 종료는 SIGTERM에서 진행 중 요청을 마치고 멈춘다(스레드는 daemon이 아님).

## 왜
- 이미지 의존을 줄여 공급망과 핀 관리 범위를 작게 한다(점검 B9; 코드로 확인: `Dockerfile`이 boundary-contracts와 jsonschema만 설치, 서버 머리말 "표준 라이브러리만 쓴다"). 클라이언트(`boundary_contracts.clients`)도 표준 라이브러리만 쓴다(D49).
- 요구가 단순(경로 6개, 본문 tar)하다.
- 이 선택의 비교 기록은 없다(**근거 기록 없음**). 위는 코드·Dockerfile에서 읽은 사실과 현재 판단이다.

## 검토한 대안과 버리는 이유 (현재 판단, 당시 비교 아님)
- FastAPI/uvicorn 등 프레임워크: 비동기와 검증 편의는 있으나 의존이 늘고 이 규모에서 이득이 측정되지 않았다(측정 안 함).
- gunicorn 등 WSGI 서버: 마찬가지로 의존 추가. 동시 요청 수가 적다는 가정.

## 결과
얻는 것: 의존 없음, 코드가 작음. 감수하는 것: HTTP 파싱 견고성·HTTP/2·keep-alive 튜닝을 프레임워크만큼 받지 못하고, 스레드 서버라 연결 상한을 직접 관리한다. TLS를 직접 종료하지 않는다(프록시 몫, ML-14).

## 되돌리는 조건
동시 소비자가 늘어 스레드 한계에 닿거나(측정 필요) 직접 구현한 HTTP 처리에서 보안 결함이 나오면 프레임워크로 옮기고 새 ADR로 대체한다.

# 0009. 레지스트리 서버 인증: 읽기 토큰과 쓰기 토큰 분리, 쓰기는 model-lab 하나

- 상태: 채택됨 (HTTP.md 규약 + 브리프 6절). 서명·TLS는 미결정(ADR 0003, runbook ML-14).

## 맥락
모델 레지스트리에 쓰는 영역은 이 영역뿐이고 게이트를 거치지 않은 모델은 서비스에 갈 수 없다(브리프 6절). 읽는 쪽은 release-gate 등이다. 비밀은 환경 변수가 아니라 파일로 받는다(D84, 2026-10-27 토큰이 `env` 출력에 노출된 사고).

## 결정
Bearer 토큰, 역할=토큰 쌍. 읽기 토큰(`MODEL_REGISTRY_READ_TOKENS`, 역할 이름은 자유 문자열)은 GET만, 쓰기 토큰(`MODEL_REGISTRY_WRITE_TOKENS`)은 POST만이고 쓰기 역할은 `model-lab`만 허용한다(다른 역할 이름은 시작 거부). 쓰기 토큰은 읽기도 된다. 토큰 비교는 상수 시간(`hmac.compare_digest`), 값은 로그·오류 응답에 쓰지 않는다. 토큰 파일은 `read_secret`(`NAME_FILE`)로 읽는다. 게시 때 역할·접속 주소·시각을 기록한다.

## 왜
- 표준: HTTP.md 11행의 토큰 규약(역할=토큰, `<이름>_TOKENS`, D84 파일 전달)과 I3 표의 "쓰기 역할 `model-lab`". 읽기 토큰의 쓰기 호출은 403이다.
- 최소 권한: 소비자(release-gate)가 침해되어도 패키지를 게시하지 못하게 한다.
- 상수 시간 비교: 토큰 길이·내용을 응답 시간으로 추측하지 못하게 하는 일반 관행.

## 토큰 강도와 실패 제한의 의미 (3차 점검 반영)
- **무차별 대입에 대한 실제 방어는 토큰의 엔트로피다.** 서비스는 시작 때 모든 토큰(읽기·쓰기)이 32자 이상이고 서로 다른 글자가 8개 이상인지 검사하고, 미달이면 시작을 거부한다(오류 메시지에 토큰 값은 넣지 않는다). 32자 무작위 16진수는 128비트다. 근거: 예측할 수 없는 비밀은 CSPRNG로 만들고 충분한 비트 수를 갖춘다는 일반 지침(OWASP 세션 관리 치트시트의 세션 ID 권고, NIST SP 800-63B의 무작위 인증 비밀) — **이번에 원문을 다시 확인하지 않았고 기억한 수준이다.** 32자라는 하한은 이 지침들의 128비트급 권고를 16진수로 환산한 값이다. 길이 검사는 엔트로피를 증명하지 못한다: 무작위로 만드는 책임은 운영자 몫이다(`openssl rand -hex 32`). 개발에서만 `MODEL_REGISTRY_MIN_TOKEN_LEN`으로 낮춘다.
- **인증 실패 제한(10회/60초/주소)은 무차별 대입 방어가 아니다.** 틀린 토큰이 쏟아질 때 로그 스팸과 토큰 비교 CPU를 줄이는 장치다. 유효한 토큰은 제한과 무관하게 통과시킨다. 이유: 프록시·Docker 뒤에서는 모든 호출자가 같은 주소로 보여, 주소 단위로 막으면 틀린 토큰 몇 번이 정상 호출자(release-gate)까지 막기 때문이다(재점검 ML-1). 이 선택의 대가는 **제한된 주소에서도 맞는 추측은 통과한다**는 것이고, 그래서 위 엔트로피 요건이 있다.

## 검토한 대안과 버리는 이유
- 사용자별 계정/OIDC: 소비자가 서비스(사람이 아님)이고 사용자 인증은 게이트웨이 몫이다(HTTP.md 68행에서 승인자 식별은 게이트웨이가 한다 — 문서로 확인). 근거 기록 없음: 레지스트리에 대해 이 대안을 비교한 기록은 없다.
- mTLS: TLS 종료 지점이 미정이다(ML-14, 사용자·헤드 결정 U5).
- 쓰기 토큰 역할 다수: 쓰기 주체가 이 영역 하나라서 불필요(브리프). 대신 행위자 구분이 주소까지뿐이다(ML-6).

## 결과
얻는 것: 단순하고 계약과 같은 모양. 감수하는 것: 토큰은 정적(만료·회전은 재시작 필요), 평문 HTTP, 읽기 역할 이름이 자유 문자열, 인증 실패는 주소별로만 센다(ADR 0007).

## 되돌리는 조건
TLS/프록시와 운영 주소가 정해지거나 쓰기 주체가 늘면 새 ADR로 대체한다.

# 0021. 토큰이 없거나 틀리면 401 + WWW-Authenticate: Bearer, 권한 부족만 403

## 상태
채택 (2026-10-29, 단계 B, 계약 CONVENTIONS.md 6절 "401과 403", 헤드 결정 D106). ADR 0009의 상태 코드 부분을 보강한다.

## 맥락
이 서버는 토큰이 없거나 틀린 요청에도 403을 냈다. 계약이 영역 사이 서비스 API도 공개 API와 같이 정했다.

## 결정
- 토큰이 없거나 틀리면 `401`과 `WWW-Authenticate: Bearer`, 본문 `code`는 `PERMISSION_DENIED`(`app.Unauthenticated`).
- 토큰은 맞지만 역할이 모자라면(읽기 토큰으로 `POST`) `403`, 헤더 없음, `code`는 `PERMISSION_DENIED`.
- `/healthz`, `/readyz`는 인증 없음 그대로.
- 인증 실패 속도 제한: 한도를 넘으면 계약 "과다 요청"의 영역 사이 규칙대로 **503 `UNAVAILABLE`**이다. 이미 503이라 바꾸지 않았다. 계약이 허용하는 `Retry-After`는 값을 정할 근거(측정)가 없어 싣지 않는다. 429는 공개 API 몫이다.

## 왜
RFC 9110 15.5.2(401은 인증 자격이 없거나 유효하지 않음, 챌린지 필수)와 11.6.1, RFC 6750 3절(Bearer 챌린지). 계약이 같은 것을 정했다. 401과 403이 구분되면 호출자가 "토큰을 고쳐야 하는지"와 "권한을 받아야 하는지"를 가린다.

## 검토한 대안과 버리는 이유
- 403 유지: 계약 위반이다.
- 403에도 `WWW-Authenticate`: 토큰이 맞아 다시 인증해도 소용없다(RFC 9110 15.5.4). 계약도 401만 말한다.

## 결과
`boundary_contracts.clients`는 401과 403을 모두 `PERMISSION_DENIED`로 읽으므로 클라이언트는 바뀌지 않는다(계약). 시험: `tests/test_auth_401.py`(raw 소켓으로 응답 줄과 헤더 확인). 기존 시험의 403 기대 4곳을 401로 고쳤다(없는/틀린 토큰인 곳만. 읽기 토큰의 쓰기 403은 그대로).

## 되돌리는 조건
계약이 바뀌면 따른다.
